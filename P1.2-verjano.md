## 1. Escenario y Datos de la Instalación (Parte 1)

En la práctica anterior (P1.1), SQLite trabajaba únicamente durante el proceso de *build* estático: el script `tools/index.py` leía los ficheros Markdown, generaba una base de datos efímera (`build/site.db`), exportaba los JSON y el servidor Nginx solo servía HTML/CSS estático.

En esta práctica damos el salto al modelo dinámico: **la base de datos SQLite pasa a ser el corazón persistente de la aplicación**. El CMS dinámico en PHP (**Chyrp Lite**) consulta SQLite en cada petición HTTP y guarda allí todas sus entradas, metadatos y etiquetas.

## 2. Exploración del Esquema de Chyrp Lite (Parte 2)

Hago una copia de seguridad para trabajar en frío:
```bash
cp ~/chyrp-datos/blog.sqlite /tmp/blog-copia.sqlite

```

### Esquema y estructura interna

```sql
sqlite> .tables
groups           modules          post_attributes  posts            sessions         settings         users

sqlite> .schema posts
CREATE TABLE "posts" (
    "id" integer NOT NULL PRIMARY KEY AUTOINCREMENT,
    "feather" varchar(32) NOT NULL,
    "clean" varchar(128) NOT NULL,
    "url" varchar(128) NOT NULL,
    "pinned" boolean NOT NULL DEFAULT '0',
    "status" varchar(32) NOT NULL DEFAULT 'public',
    "user_id" integer NOT NULL,
    "created_at" datetime DEFAULT NULL,
    "updated_at" datetime DEFAULT NULL
);
CREATE INDEX "posts_clean" ON "posts" ("clean");
CREATE INDEX "posts_url" ON "posts" ("url");
CREATE INDEX "posts_created_at" ON "posts" ("created_at");

sqlite> .schema post_attributes
CREATE TABLE "post_attributes" (
    "post_id" integer NOT NULL,
    "name" varchar(128) NOT NULL,
    "value" longtext,
    PRIMARY KEY ("post_id", "name")
);
CREATE INDEX "post_attributes_name" ON "post_attributes" ("name");
```

### Preguntas de análisis del esquema

1. **¿Qué tablas hay y para qué sirve cada una?**
   * `posts`: Guarda la cabecera/metadatos obligatorios de cada entrada (identificador, autor, fechas, estado y slug para rutas).
   * `post_attributes`: Almacena el contenido dinámico mediante el modelo **EAV (Entity-Attribute-Value)**: título, cuerpo y etiquetas.
   * `users`: Cuentas de usuario locales, login, contraseñas hasheadas y grupo al que pertenecen.
   * `groups` y `permissions`: Gestión de permisos por roles (RBAC) para administración y edición.
   * `modules`: Registro de extensiones habilitadas (ej. `tags`).
   * `sessions`: Tokens de sesión activa para usuarios autenticados.
   * `settings`: Claves y valores de configuración global del blog (nombre, descripción, tema, zona horaria).

2. **¿Cuántas filas ocupa cada entrada en cada tabla? ¿Dónde está el título y el cuerpo?**
   * Cada entrada ocupa exactamente **1 fila** en la tabla `posts`.
   * En `post_attributes`, una entrada típica ocupa **3 filas**:
     * `(post_id, 'title', 'Texto del título')`
     * `(post_id, 'body', 'Contenido en Markdown...')`
     * `(post_id, 'tags', '{"prueba":"prueba","sql":"sql"}')`

3. **¿Qué clave primaria tiene `post_attributes`? ¿Por qué es compuesta? ¿Qué clave foránea lleva?**
   * Clave primaria: `PRIMARY KEY ("post_id", "name")`.
   * Es compuesta porque un atributo (`name`) solo puede aparecer una vez por cada entrada. Evita que un post tenga dos títulos o dos cuerpos duplicados.
   * Clave foránea: `post_id` referencia a `posts(id)` (con borrado en cascada para no dejar atributos huérfanos).

4. **¿Existe una tabla de etiquetas? ¿Cómo se guardan?**
   * **No existe tabla de etiquetas.** Chyrp Lite utiliza el módulo `Tags` que serializa todas las etiquetas de una entrada dentro de una única fila en `post_attributes` donde `name = 'tags'`.
   * El formato de `value` es un objeto JSON asociativo `{ "nombre": "slug" }` (ejemplo: `{"prueba":"prueba","sql":"sql"}`).
   * En la entrada de prueba sin etiquetas, el campo almacena literalmente un array vacío: `[]`.

5. **¿Cómo se guarda la fecha? ¿Qué valor tiene `updated_at` si nunca se editó?**
   * Las fechas se guardan como cadenas de texto con formato estándar ISO: `YYYY-MM-DD HH:MM:SS`.
   * En una entrada que nunca se ha editado, Chyrp Lite asigna el valor centinela constante `1000-01-01 00:00:00` (`SQL_DATETIME_ZERO`) para evitar problemas con valores `NULL` al ordenar en distintas bases de datos.

6. **¿Qué diferencia hay entre `clean` y `url` en `posts`? ¿Qué valores toma `status`?**
   * `clean` es la versión normalizada y "limpia" del título (slug sin tildes ni caracteres extraños).
   * `url` es el identificador único con el que el enrutador de Chyrp Lite busca la entrada al resolver peticiones HTTP.
   * `status` puede tomar los valores `'public'`, `'draft'`, `'pinned'` o `'private'`.

7. **Ventajas y desventajas del modelo EAV (Entity-Attribute-Value):**
   * **Ventaja:** Máxima flexibilidad y extensibilidad modular. Si mañana instalamos un módulo de audio o de valoración por estrellas, este puede añadir sus atributos (`rating`, `audio_url`) sin necesidad de ejecutar un `ALTER TABLE` que bloquee la tabla principal ni dejar columnas vacías llenas de `NULL`.
   * **Desventaja:** Degradación del rendimiento y dificultad para consultas relacionales. Para reconstruir una entrada completa hay que hacer múltiples JOINs o subconsultas. Además, se pierde la tipificación estricta del motor de bases de datos (todo es `TEXT`).

## 3. Correspondencia entre Esquemas (Parte 3)

### Esquema del prototipo Hugo (`build/site.db`)
* `posts(url TEXT PK, title TEXT, date TEXT, summary TEXT, body TEXT)`
* `tags(url TEXT, tag TEXT, PRIMARY KEY (url, tag))`
* Relación normalizada 1:N entre posts y tags.

### Tabla de correspondencia campo a campo

| Campo en Prototipo Hugo (P1.1) | -> | Destino en Chyrp Lite (Tabla.Columna / Atributo) | Transformación necesaria |
| :--- | :---: | :--- | :--- |
| **Título (`title`)** | -> | `post_attributes(name='title').value` | Copia directa del texto. |
| **Cuerpo (`cuerpo` del `.md`)** | -> | `post_attributes(name='body').value` | Copia íntegra en Markdown (Chyrp Lite renderiza Markdown directamente). No se usa `site.db` porque `plain()` eliminó el formato. |
| **Fecha (`date`)** | -> | `posts.created_at` | Normalización a `YYYY-MM-DD HH:MM:SS` mediante `fecha_chyrp()`. |
| **Nombre del fichero (`.stem`)** | -> | `posts.clean` y `posts.url` | Sanitización mediante `slugify()` (minúsculas, sin tildes, guiones). |
| **`summary` / `description`** | -> | *Sin equivalente* | Se omite (Chyrp Lite genera el extracto al vuelo). |
| **Etiquetas (`tags`)** | -> | `post_attributes(name='tags').value` | Conversión de lista a JSON asociativo `{tag: slug}` o `[]` si está vacía. |
| **`draft: true`** | -> | `posts.status` | Si `draft` es `true` se asigna `'draft'`; si es `false`, `'public'`. |
| **Autor** | -> | `posts.user_id` | Se asocia al ID del usuario administrador obtenido con `buscar_autor()`. |
| **Metadatos Chyrp Lite sin origen** | -> | `feather='text'`, `pinned=0`, `updated_at='1000-01-01 00:00:00'` | Valores por defecto del motor. |

## 4. El Script de Migración ETL: Lectura Guiada (Parte 4)

El script `tools/migrar.py` sigue una arquitectura funcional inspirada en la filosofía Unix:

1. **¿Qué funciones tocan disco o SQL y cuáles no? ¿Por qué `test_migrar.py` puede probar `transformar` sin base de datos?**
   * **Funciones puras (sin efectos secundarios):** `slugify()`, `fecha_chyrp()`, `etiquetas_json()`, `transformar()` y `transformar_pagina()`. Dado un mismo diccionario de entrada, devuelven siempre exactamente el mismo resultado y no modifican variables globales.
   * **Funciones impuras:** `leer_entrada()`, `extraer()` (tocan disco); `comprobar_destino()`, `buscar_autor()`, `existe()`, `insertar()` y `cargar()` (tocan SQL).
   * `test_migrar.py` puede validar `transformar()` sin base de datos porque es una función pura: solo toma datos en memoria y genera diccionarios en memoria.

2. **¿Dónde empieza y termina la transacción? ¿Qué pasaría si falla el INSERT de la 3ª entrada?**
   * La transacción empieza y termina en el bloque `with con:` dentro de la función `cargar()`:
     ```python
     with con:  # Inicia transacción implícita
         for fila in filas:
             ...
     ```
   * Si el INSERT de la 3ª entrada falla con un error (ej. disco lleno o restricción rota), el context manager de Python ejecuta automáticamente un `ROLLBACK`. Ninguna de las entradas anteriores se consolida; la base de datos queda exactamente en el estado original (**Atomicidad ACID**).

3. **¿Qué columna usa el script para saber que una entrada ya está migrada? ¿Es una buena elección? ¿Qué pasaría con dos ficheros con el mismo nombre en carpetas distintas?**
   * Usa `posts.url`. Es una elección adecuada porque Chyrp Lite exige unicidad en las URLs para poder resolver las rutas web.
   * Si hubiera dos ficheros con el mismo nombre en carpetas distintas (`posts/redes/hola.md` y `posts/sgbd/hola.md`), ambos tendrían `slug = "hola"`. El segundo fichero sería detectado por `existe(con, "hola")` y sería marcado como `omitida`, perdiéndose su contenido. Para resolverlo habría que prefijar el directorio al slug.

4. **¿Por qué `etiquetas_json` devuelve `[]` y no `{}` cuando no hay etiquetas?**
   * Porque es la convención que utiliza el código fuente PHP del módulo `Tags` de Chyrp Lite: cuando un post no tiene etiquetas asignadas, guarda `[]` (array vacío serializado en JSON). Si guardara `{}` (objeto vacío), el motor PHP generaría avisos de tipo al deserializarlo.

5. **¿Por qué `updated_at` vale `1000-01-01 00:00:00`?**
   * Proviene de la constante `SQL_DATETIME_ZERO` que Chyrp Lite utiliza en sus modelos para representar "fecha no asignada / registro sin modificaciones", evitando discrepancias al comparar fechas `NULL` entre SQLite, MySQL y PostgreSQL.

6. **¿Por qué se usa `cur.lastrowid` entre los dos INSERT?**
   * Porque la tabla `posts` genera su clave primaria `id` de forma automática (`AUTOINCREMENT`). Al insertar el post, `cur.lastrowid` devuelve el ID recién asignado en esa sesión para poder enlazarlo de inmediato como clave foránea (`post_id`) en `post_attributes`.

### Ejercicio 1: Romper la transacción a propósito

* **Qué cambié:** Introduje una excepción artificial en la función `insertar()` al procesar el tercer post:
  ```python
  if cur.lastrowid == 3:
      raise RuntimeError("Fallo inducido para probar la transacción")
  ```
* **Comprobación A (Con `with con:`):**
  Ejecuté sobre una base de datos limpia de pruebas. El script abortó con la excepción. Al consultar con `sqlite3`:
  ```sql
  SELECT COUNT(*) FROM posts; -- Resultado: 2 (solo las de prueba, 0 migradas)
  SELECT COUNT(*) FROM post_attributes; -- Resultado: 5 (ningún atributo huérfano)
  ```
  **Conclusión:** El bloque `with con:` capturó el fallo y ejecutó un `ROLLBACK` completo.
* **Comprobación B (Sin `with con:`, con `con.isolation_level = None` o autocommit):**
  Las 2 primeras entradas quedaron grabadas en `posts` y `post_attributes`, mientras que las restantes 3 no se crearon.
  **Aprendizaje:** Una migración ETL sin transacciones atómicas deja bases de datos corruptas a medio migrar cuando surge cualquier error imprevisto.

### Ejercicio 6: Un informe de etiquetas (Comparativa SQL)

* **En el prototipo normalizado (P1.1):**
  ```sql
  SELECT tag, COUNT(*) AS total
  FROM tags
  GROUP BY tag
  ORDER BY total DESC, tag;
  ```
  *Explicación:* Consulta limpia, directa, que utiliza índices relacionales y cumple la 1ª Forma Normal (1FN).

* **En Chyrp Lite (Desnormalizado / EAV con JSON):**
  ```sql
  SELECT json_each.key AS tag, COUNT(*) AS total
  FROM post_attributes, json_each(post_attributes.value)
  WHERE name = 'tags'
  GROUP BY json_each.key
  ORDER BY total DESC, tag;
  ```
* **Por qué es más difícil en Chyrp Lite:**
  Porque las etiquetas están empaquetadas en un único campo de texto JSON. Para analizarlas hay que invocar la función `json_each()` para descomprimir cada fila en subfilas al vuelo. Esto impide usar índices tradicionales de clave foránea e incrementa el coste de CPU por cada lectura.

## 7. Mini-reto: Análisis de una Entrada Creada desde el Panel

1. Desde el panel web (*Write*), publiqué una nueva entrada con título *"Entrada del mini reto"* y etiquetas `sql` (existente) y `minireto` (nueva).
2. Consulté las filas creadas:
   ```sql
   SELECT * FROM posts WHERE clean = 'entrada-del-mini-reto';
   -- Crea 1 fila en posts (id=8, clean='entrada-del-mini-reto', status='public')

   SELECT * FROM post_attributes WHERE post_id = 8;
   -- Crea 3 filas en post_attributes:
   -- 8 | title | Entrada del mini reto
   -- 8 | body  | Contenido creado desde el editor web de Chyrp Lite
   -- 8 | tags  | {"sql":"sql","minireto":"minireto"}
   ```
3. **¿Por qué más de una fila?**
   Porque cada par atributo-valor se segrega verticalmente en el modelo EAV para no alterar la estructura fija de la tabla `posts`.
4. **Consulta con `LIKE` vs `JOIN`:**
   * Con `LIKE`: `SELECT * FROM post_attributes WHERE name = 'tags' AND value LIKE '%:"sql"%';`
   * Es menos rigurosa porque si una etiqueta se llama `mysql`, un `LIKE '%sql%'` mal delimitado podría generar falsos positivos, mientras que un `JOIN tags WHERE tag = 'sql'` en un modelo relacional normalizado es exacto e indexado.

## 8. Preguntas para Reflexionar

1. **Disponibilidad en producción (P1.1 vs P1.2):**
   * En la P1.1 (Hugo), si SQLite fallaba, el sitio web en producción **seguía funcionando al 100%**, porque Nginx solo servía HTML estático ya compilado.
   * En Chyrp Lite, la base de datos está en el camino crítico de cada petición HTTP. Si SQLite se bloquea, se corrompe o se agotan los permisos, el blog completo deja de responder inmediatamente (error 500 / pantalla blanca).

2. **Concurrencia en SQLite:**
   * SQLite bloquea el fichero completo durante las escrituras (`database is locked`). Si decenas de usuarios intentan comentar o publicar a la vez, se formarán colas de espera y errores de tiempo límite (timeout).
   * Tendría sentido migrar a **PostgreSQL o MySQL** en cuanto haya alta concurrencia de escritura, múltiples editores simultáneos o necesidad de escalado horizontal con varios servidores de aplicaciones conectados a un mismo nodo de datos.

3. **Copias de seguridad:**
   * En Hugo no era necesario hacer backup de la base de datos `site.db` porque los ficheros Markdown y el repositorio Git eran la **fuente de la verdad**.
   * En Chyrp Lite, la base de datos `blog.sqlite` **es la fuente de la verdad**. Si se pierde o se borra, se pierde todo el blog de forma irreversible. El backup debe incluir obligatoriamente el fichero `.sqlite` (o un dump generado con `sqlite3 blog.sqlite .dump`).

4. **Normalización (1FN) y diseño EAV:**
   * Guardar `{"tag1":"tag1","tag2":"tag2"}` en una columna vulnera la Primera Forma Normal (los atributos deben ser atómicos).
   * Se pierden comprobaciones de integridad referencial, índices y velocidad analítica.
   * Chyrp Lite gana a cambio una gran **flexibilidad modular**: los módulos pueden inventar y guardar nuevos atributos sin tocar la estructura física de la base de datos.

5. **Riesgos de escribir directamente en la base de datos:**
   * Se salta la lógica de negocio del CMS (sanitización de HTML, triggers internos, purgado de cachés Twig y hooks de módulos).
   * La alternativa recomendada si existiera sería una API REST o un importador nativo que valide las entradas a través de los propios controladores de la aplicación.

6. **¿Por qué el módulo Migration de Chyrp Lite no servía?**
   * Porque solo trae conectores para otros CMS tradicionales (WordPress, Tumblr, MovableType) basados en volcados SQL o exportaciones XML estándar de blogs dinámicos. Para migrar desde ficheros Markdown con front matter YAML de un generador estático como Hugo se requiere un ETL a medida como el desarrollado en esta práctica.
