## 1. Introducción y Contexto Tecnológico

En el módulo de SGBD hemos analizado en profundidad la pregunta fundamental de la arquitectura web: **«¿Dónde vive el contenido de una aplicación web y cómo se gestiona su persistencia?»**. A lo largo de esta trilogía de prácticas hemos evolucionado la infraestructura paso a paso:

1. **P1.1 (Hugo + SQLite):** Un prototipo didáctico donde la base de datos SQLite trabajaba únicamente durante la fase de compilación (*build time*). SQLite leía el Markdown y generaba índices estáticos en formato JSON (`search.json`, `tags.json`, `stats.json`). En producción no existía ningún motor de base de datos activo, solo un servidor web Nginx sirviendo ficheros estáticos.
2. **P1.2 (Hugo a Chyrp Lite + SQLite):** La base de datos pasó a ser el corazón dinámico de la aplicación en tiempo de ejecución (*runtime*). Implementamos el CMS Chyrp Lite y desarrollamos un script ETL (`tools/migrar.py`) para volcar el contenido desde Markdown hacia una base de datos local SQLite (`blog.sqlite`), estructurada con el patrón EAV (*Entity-Attribute-Value*).
3. **P1.3 (Chyrp Lite + SQLite a MariaDB):** Damos el salto definitivo de infraestructura, migrando de un motor embebido monousuario basado en un único fichero local (`.sqlite`) a un **servidor de bases de datos relacional cliente/servidor real (MariaDB)**.

```text
       PRÁCTICA 1.1                           PRÁCTICA 1.2                           PRÁCTICA 1.3
┌────────────────────────┐             ┌────────────────────────┐             ┌────────────────────────┐
│   Hugo + SQLite        │             │  Chyrp Lite + SQLite   │             │  Chyrp Lite + MariaDB  │
├────────────────────────┤             ├────────────────────────┤             ├────────────────────────┤
│ SQLite en BUILD TIME   │             │ SQLite en RUNTIME      │             │ MariaDB CLIENTE/SRV    │
│ Genera JSON estáticos  │    ────►    │ Un fichero local en    │    ────►    │ Demonio mysqld de red  │
│ Sin BD en producción   │             │ disco (blog.sqlite)    │             │ InnoDB, row-locking    │
│ Solo lectura en web    │             │ Bloqueo a nivel archivo│             │ Concurrencia y ACID    │
└────────────────────────┘             └────────────────────────┘             └────────────────────────┘
```

Esta práctica tiene como objetivo comprender las diferencias de arquitectura entre ambos motores, implementar un filtro Unix en Python (`tools/sqlite2maria.py`) que genera un volcado SQL limpio, transaccional e idempotente, y validar la persistencia íntegra de los datos en el servidor MariaDB.

## 3. Parte 2: Arquitectura y Comparativa entre SQLite y MariaDB

Durante el desarrollo de la práctica hemos analizado las diferencias de fondo entre ambos motores de bases de datos:

| Característica | SQLite 3 | MariaDB (InnoDB) |
|:---|:---|:---|
| **Modelo de Arquitectura** | Embebido en la aplicación (in-process library). No hay proceso servidor ni demonio. | Cliente/Servidor. Un proceso demonio de sistema (`mariadbd`) escucha en sockets o TCP (puerto 3306). |
| **Almacenamiento físico** | Un único fichero ordinario en el sistema de ficheros (`blog.sqlite`). | Espacio de tablas estructurado (`/var/lib/mysql/ibdata1`, `.ibd` por tabla con `innodb_file_per_table`). |
| **Mecanismo de Bloqueo** | Bloqueo a nivel de toda la base de datos (*file locking* con `fcntl` / `flock`). Una escritura bloquea cualquier otra lectura/escritura. | Bloqueo granular a nivel de fila (*row-level locking*) mediante el motor transaccional `InnoDB`. |
| **Concurrencia** | Excelente para lecturas concurrentes, pero cuello de botella severo ante escrituras simultáneas concurrentes. | Altísima concurrencia: múltiples clientes pueden escribir y leer en la misma tabla simultáneamente sin bloquearse. |
| **Sistema de Tipos** | **Tipado dinámico / Afinidad de tipos:** Una columna declarada como `INTEGER` puede almacenar texto sin arrojar error. | **Tipado estricto:** Los tipos de datos se verifican en tiempo de inserción (`INT`, `VARCHAR`, `DATETIME`). |
| **Claves Primarias Autoincrementales** | `INTEGER PRIMARY KEY AUTOINCREMENT`. Gestiona el contador en una tabla interna `sqlite_sequence`. | `INT NOT NULL AUTO_INCREMENT PRIMARY KEY`. El puntero se almacena en memoria y en las cabeceras del motor InnoDB. |
| **Tipos Booleanos** | No existe tipo booleano nativo. Almacena enteros `0` o `1` con afinidad `INTEGER`. | Utiliza `TINYINT(1)` (alias sintáctico de `BOOLEAN`). `0` es falso, `1` es verdadero. |
| **Fechas y Tiempos** | No hay tipo nativo. Se almacenan como cadenas ISO-8601 (`TEXT`), enteros Unix epoch (`INTEGER`) o coma flotante juliana (`REAL`). | Tipos dedicados de fecha y hora: `DATETIME`, `TIMESTAMP`, `DATE`. Permiten operaciones aritméticas y conversiones de huso horario nativas. |
| **Cotejamiento (Collation)** | Por defecto sensible a mayúsculas (`BINARY`). El operador `LIKE` es insensible a mayúsculas solo para caracteres ASCII de 7 bits. | Cotejamiento configurable a nivel de servidor, base de datos y columna (`utf8mb4_unicode_ci` / `utf8mb4_general_ci`), insensible a mayúsculas y acentos (`CI`). |
| **Control de Acceso y Red** | Basado únicamente en los permisos del sistema de ficheros del sistema operativo (`chmod`, `chown`). | Sistema avanzado de autenticación y privilegios basado en usuarios, hosts de origen (`'chyrp'@'localhost'`), roles y permisos granulares. |
| **Copias de Seguridad** | Copia directa del fichero (o comando `.backup` en sqlite3). Requiere precaución con escrituras concurrentes. | Copias en caliente consistentes y transaccionales mediante `mariadb-dump` / `mysqldump` con `--single-transaction`. |

## 4. Parte 3: Correspondencia de Esquemas (Tablas de Chyrp Lite)

Examinando los esquemas generados por Chyrp Lite en ambos motores, observamos cómo el CMS adapta su modelo de datos al dialecto específico de cada gestor:

### 4.1. Tabla `posts`
Representa las entradas publicadas en el blog.

```sql
-- En SQLite (P1.2):
CREATE TABLE posts (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    feather TEXT DEFAULT 'text',
    clean TEXT,
    url TEXT,
    pinned INTEGER DEFAULT 0,
    status TEXT DEFAULT 'public',
    user_id INTEGER DEFAULT 0,
    created_at TEXT,
    updated_at TEXT
);

-- En MariaDB (P1.3):
CREATE TABLE `posts` (
    `id` int(11) NOT NULL AUTO_INCREMENT,
    `feather` varchar(32) DEFAULT 'text',
    `clean` varchar(128) DEFAULT '',
    `url` varchar(128) DEFAULT '',
    `pinned` tinyint(1) DEFAULT 0,
    `status` varchar(32) DEFAULT 'public',
    `user_id` int(11) DEFAULT 0,
    `created_at` datetime DEFAULT NULL,
    `updated_at` datetime DEFAULT NULL,
    PRIMARY KEY (`id`),
    KEY `clean` (`clean`),
    KEY `created_at` (`created_at`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;
```

**Mapeo de tipos:**
* `id`: `INTEGER PRIMARY KEY AUTOINCREMENT` en SQLite ──► `int(11) NOT NULL AUTO_INCREMENT PRIMARY KEY` en MariaDB.
* `pinned`: `INTEGER DEFAULT 0` en SQLite ──► `tinyint(1) DEFAULT 0` en MariaDB.
* `created_at` / `updated_at`: `TEXT` en SQLite ──► `datetime DEFAULT NULL` en MariaDB.
* Índices: En MariaDB se definen índices explícitos sobre `clean` y `created_at` para acelerar consultas de ordenación y filtrado web.

### 4.2. Tabla `post_attributes`
Implementa el modelo EAV (*Entity-Attribute-Value*) de Chyrp Lite, donde residen el título, el cuerpo en Markdown y las etiquetas en JSON.

```sql
-- En SQLite (P1.2):
CREATE TABLE post_attributes (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    post_id INTEGER,
    name TEXT,
    value TEXT
);

-- En MariaDB (P1.3):
CREATE TABLE `post_attributes` (
    `id` int(11) NOT NULL AUTO_INCREMENT,
    `post_id` int(11) NOT NULL,
    `name` varchar(250) DEFAULT '',
    `value` longtext DEFAULT NULL,
    PRIMARY KEY (`id`),
    KEY `post_id` (`post_id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;
```

**Mapeo de tipos:**
* `value`: `TEXT` en SQLite (sin límite definido) ──► `longtext` en MariaDB (capacidad de hasta 4 GB de contenido textual para artículos largos).
* `post_id`: `INTEGER` sin índice ──► `int(11) NOT NULL` con índice `KEY (post_id)`.

## 5. Parte 4: El Script de Migración (`tools/sqlite2maria.py`)

Siguiendo la filosofía Unix, el script `tools/sqlite2maria.py` está diseñado como un **filtro de datos puro**:
* **Entrada:** Lee el fichero `.sqlite` origen en modo solo lectura (`file:...mode=ro`).
* **Salida estándar (`stdout`):** Emite sentencias SQL estándar compatibles con MariaDB.
* **Salida de error (`stderr`):** Muestra el progreso de filas procesadas por tabla.
* **Consumo:** El cliente oficial `mariadb` se encarga de inyectar las sentencias en el motor, desacoplando completamente la lógica de transformación de los controladores de red.

```text
 ┌──────────────────────┐
 │  copia.sqlite        │
 │  (SQLite de Chyrp)   │
 └──────────┬───────────┘
            │
            ▼ (solo lectura)
 ┌──────────────────────┐
 │ tools/sqlite2maria.py│ ◄── Funciones puras (literal, ident, lotes, sentencias_tabla, volcado)
 └──────────┬───────────┘
            │
            ├──────────────► [stderr]: "sqlite2maria: posts 5 filas" (información)
            ▼ [stdout]
 ┌──────────────────────┐
 │   build/chyrp.sql    │ ◄── Transaccional, DELETE previo, lotes de INSERT, SET NAMES utf8mb4
 └──────────┬───────────┘
            │
            ▼ (tubería Unix)
 ┌──────────────────────┐
 │ mariadb -u chyrp ... │ ──► Base de datos 'chyrp' en servidor MariaDB
 └──────────────────────┘
```

### 5.1. Estructura del código: separación estricta de funciones puras y efectos

El script mantiene una separación matemática estricta entre:
* **Funciones puras (sin efectos secundarios, testeables al 100% en memoria):**
  * `literal(valor)`: Convierte tipos de datos de Python a literales SQL válidos en MariaDB. Duplica comillas simples (`'`), escapa barras invertidas (`\`), convierte booleanos a `1`/`0`, nulos a `NULL` y datos binarios a `X'hex'`.
  * `ident(nombre)`: Enmarca nombres de tabla y columna entre comillas invertidas de MySQL (` `posts` `).
  * `lotes(filas, tamano)`: Segmenta listas grandes en lotes de tamaño configurable (por defecto 100 filas por `INSERT`).
  * `insert_lote(tabla, columnas, filas)`: Construye sentencias multi-fila de alta velocidad (`INSERT INTO tabla (col1, col2) VALUES (...), (...);`).
  * `sentencias_tabla(tabla, columnas, filas, tamano)`: Genera un `DELETE FROM tabla;` seguido de los bloques de `INSERT`.
  * `volcado(tablas, tamano)`: Ensambla el preámbulo transaccional, las sentencias de cada tabla y el epílogo.
* **Funciones de efecto (I/O):**
  * `listar_tablas(con, excluir)`: Consulta `sqlite_master` para obtener las tablas de usuario excluyendo las del sistema y las ignoradas.
  * `leer_tabla(con, tabla)`: Ejecuta `SELECT *` y recupera nombres de columnas y registros.
  * `main()`: Procesa argumentos de CLI y conecta la entrada y salida.

### 5.2. Respuestas a las Preguntas Guiadas de Lectura (Apartado 4.4)

A continuación se responde en detalle y con rigor técnico a las 6 cuestiones planteadas en el guion de la práctica:

#### 1. ¿Por qué el script NO genera sentencias `CREATE TABLE`?
El script no genera sentencias `CREATE TABLE` porque **Chyrp Lite ya se encarga de crear el esquema completo con sus tipos de datos, índices, claves primarias y opciones de almacenamiento específicas de MariaDB durante su instalación web (`install.php`)**.
Si el script intentara generar sentencias DDL (`CREATE TABLE`), tendría que traducir manualmente las particularidades sintácticas entre SQLite y MariaDB (por ejemplo, `AUTOINCREMENT` frente a `AUTO_INCREMENT`, o tipos `TEXT` frente a `VARCHAR`/`DATETIME`). Esta tarea es propensa a errores y acoplamientos innecesarios. Al asumir que las tablas ya existen en el destino, el script se enfoca exclusivamente en la migración de datos (`DML`), respetando la definición canónica del software.

#### 2. ¿Por qué se utiliza `DELETE FROM tabla` antes de los `INSERT` en lugar de `TRUNCATE TABLE`?
En MySQL y MariaDB, la orden `TRUNCATE TABLE` es una operación de definición de datos (**DDL**) que recrea internamente la tabla en disco. Como consecuencia del estándar de estos motores, **`TRUNCATE` fuerza un `COMMIT` implícito automático e irrevocable**, rompiendo cualquier transacción abierta.
Si utilizáramos `TRUNCATE` y ocurriese un error a mitad de la migración, la transacción no se podría revertir con `ROLLBACK`, dejando la base de datos vacía o corrupta.
Por el contrario, la sentencia `DELETE FROM tabla;` es una operación de manipulación de datos (**DML**) que **se ejecuta dentro del bloque transaccional (`START TRANSACTION ... COMMIT`)**. Esto garantiza la propiedad de **atomicidad (ACID)**: o se aplican todos los cambios de todas las tablas con éxito, o se descarta todo de manera limpia y sin efectos colaterales.

#### 3. ¿Por qué se deshabilitan las comprobaciones de claves foráneas con `SET FOREIGN_KEY_CHECKS=0` al inicio y se reactivan al final?
En MariaDB con motor InnoDB, las restricciones de clave foránea (*Foreign Keys*) impiden vaciar tablas que estén referenciadas por otras o insertar registros hijos antes de que existan los registros padres en la tabla referenciada (por ejemplo, registros en `post_attributes` que dependen del `id` en `posts`).
Al establecer `SET FOREIGN_KEY_CHECKS=0;` en el preámbulo:
* Las tablas pueden vaciarse (`DELETE`) e insertarse (`INSERT`) en cualquier orden sin generar errores de integridad referencial temporal durante la carga en masa.
* Se optimiza significativamente la velocidad de inserción al posponer la validación pesada de restricciones hasta que toda la información ha sido cargada.
* En el epílogo del volcado se ejecuta `SET FOREIGN_KEY_CHECKS=1;`, restableciendo la integridad referencial para el funcionamiento ordinario de la aplicación.

#### 4. ¿Por qué es fundamental incluir `SET NAMES utf8mb4` al principio del volcado?
La sentencia `SET NAMES utf8mb4;` configura tres variables críticas de la sesión cliente-servidor de MariaDB:
* `character_set_client = utf8mb4`
* `character_set_connection = utf8mb4`
* `character_set_results = utf8mb4`

En MariaDB, la codificación histórica `utf8` (alias de `utf8mb3`) solo utiliza 3 bytes por carácter, lo que corrompe o trunca caracteres suplementarios de 4 bytes, tales como emoticonos (`🔄`), caracteres matemáticos o símbolos tipográficos avanzados. Además, si el cliente se conecta por defecto con juego de caracteres `latin1`, los caracteres acentuados del castellano (á, é, í, ó, ú, ñ) sufren un problema de doble codificación o corrupción conocido como *mojibake*. Con `SET NAMES utf8mb4` aseguramos que tanto los acentos como cualquier símbolo Unicode de 4 bytes se transmiten y almacenan con total fidelidad.

#### 5. ¿Por qué se excluye la tabla `sessions` por defecto del volcado?
La tabla `sessions` almacena tokens efímeros y marcas de tiempo de sesiones HTTP activas en el navegador. Excluirla es una buena práctica de administración de sistemas por tres motivos:
1. **Caducidad temporal:** Las sesiones generadas en la máquina local sobre SQLite habrán expirado o contendrán hashes no válidos en el nuevo entorno.
2. **Seguridad:** Evita transferir identificadores de sesión en ficheros de texto plano (`.sql`).
3. **Colisiones:** Al iniciar sesión en la nueva instalación de Chyrp Lite sobre MariaDB, el CMS creará sesiones limpias sin riesgo de inconsistencias con identificadores de usuario huérfanos.

#### 6. ¿Cómo viajan los ficheros subidos (`uploads/`) y la configuración (`config.json.php`)?
Los ficheros subidos (`uploads/`) y la configuración de Chyrp Lite (`includes/config.json.php`) **no viven en la base de datos ni pueden viajar en un volcado SQL**.
* Los ficheros binarios adjuntos (imágenes, PDFs, multimedia) se almacenan en el sistema de ficheros del servidor web. Deben transferirse a nivel de sistema operativo utilizando herramientas de sincronización como `rsync` o `scp`:
  ```bash
  rsync -avz /var/www/chyrp-sqlite/uploads/ /var/www/chyrp-maria/uploads/
  ```
* El fichero `includes/config.json.php` contiene la configuración específica del adaptador de base de datos (`adapter: "mysql"` frente a `"sqlite"`, credenciales, host y puerto). No debe sobreescribirse con el de SQLite, sino que debe mantenerse el generado por el instalador de MariaDB.

### 6.2. Generación del volcado SQL con el Makefile

## 8. Parte 7: Conclusiones Técnicas de Administración de Sistemas

A través de esta serie de prácticas hemos experimentado de primera mano las implicaciones de arquitectura al elegir un motor de bases de datos:

1. **Cuándo elegir SQLite:**
   * Prototipos, herramientas CLI, aplicaciones de escritorio o móviles y sitios web estáticos o con bajo volumen de visitas donde el 95%+ de las operaciones son lecturas.
   * Su ventaja radical es la simplicidad operativa (*zero-configuration*): no requiere demonios en segundo plano, puertos abiertos en el cortafuegos ni administración de usuarios. Sin embargo, su bloqueo a nivel de fichero lo descarta para entornos con concurrencia masiva de escritura.

2. **Cuándo elegir MariaDB / MySQL:**
   * Aplicaciones dinámicas con múltiples usuarios concurrentes (CMS, comercio electrónico, ERPs) que requieren procesamiento transaccional fiable bajo el estándar ACID.
   * Su arquitectura cliente-servidor con motor InnoDB permite concurrencia masiva gracias al bloqueo por fila, gestión de réplicas en clúster (Galera), copias de seguridad en caliente con `mariadb-dump` y políticas de seguridad avanzadas a nivel de red y privilegios.

3. **La elegancia de la arquitectura como filtro Unix:**
   * Mantener el script de migración (`sqlite2maria.py`) como un filtro puro en Python que genera SQL en la salida estándar ha demostrado ser una decisión de diseño limpia y desacoplada: no requiere dependencias externas de librerías de conexión (`mysql-connector`), es testeable mediante pruebas unitarias en memoria en milisegundos y permite encadenar tuberías Unix estándar para el despliegue automatizado.
